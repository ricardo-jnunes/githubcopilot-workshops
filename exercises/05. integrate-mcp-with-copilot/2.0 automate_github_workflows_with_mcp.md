# Automate GitHub Workflows with MCP: Branches, Pull Requests & Issues

## Workshop objectives

By the end of this exercise, you will be able to:

- use GitHub Copilot with the GitHub MCP server;
- inspect repository data before taking an action;
- create a branch and track work with an issue;
- open and update a pull request through natural-language instructions;
- use Copilot to review the result while keeping a human in control of write operations.

## Scenario

You are contributing a small documentation improvement to a GitHub repository. You will use the GitHub MCP server to discover the repository state, create a working branch, create an issue, open a pull request, and add a follow-up comment.

Use a repository where you have permission to create branches, issues, and pull requests. A workshop repository or a fork is recommended.

## Prerequisites

1. GitHub Copilot is available in VS Code.
2. A GitHub MCP server is configured and enabled for Copilot.
3. You are signed in to an account with write access to the selected repository.
4. You know the repository owner and name, for example `octo-org/octo-repo`.

### Configure the GitHub MCP server in VS Code

1. Open the Command Palette with `Ctrl+Shift+P` and run `MCP: Add Server`.
2. Select `HTTP` as the server type.
3. Enter the GitHub MCP server URL:

	 ```text
	 https://api.githubcopilot.com/mcp/
	 ```

4. Give the server a recognizable name, such as `github`.
5. Choose whether to save the configuration in the workspace or in your user profile. Use the workspace configuration when the whole workshop team should use the same setup; use the user profile for a personal configuration.
6. When VS Code asks for authorization, sign in to GitHub and approve only the access required for this exercise.
7. Open the MCP view, locate the `github` server, and start it if it is not already running.

You can also add the server manually to `.vscode/mcp.json`:

```json
{
	"servers": {
		"github": {
			"type": "http",
			"url": "https://api.githubcopilot.com/mcp/"
		}
	}
}
```

Do not commit tokens or credentials to the repository. If your organization provides a different GitHub MCP endpoint or restricts OAuth applications, follow that organization's endpoint and approval process.

Before making changes, ask Copilot to verify the connection:

> Using the GitHub MCP server, inspect the repository `OWNER/REPOSITORY`. List the default branch and the open issues. Do not create, update, or delete anything yet. Summarize what you found.

Check that the response identifies the intended repository and that Copilot can read its branches and issues. This read-only check prevents actions from being sent to the wrong repository.

## Exercise 1: Plan from the repository state

Choose a small improvement, such as fixing a broken link or clarifying an installation step. Ask Copilot to investigate before proposing work:

> Search the issues in `OWNER/REPOSITORY` for an open issue related to documentation, onboarding, or broken links. Read the most relevant issue and inspect the files it mentions. Do not modify the repository. Recommend a small change and explain why it is appropriate.

Discuss the answer with your team. Confirm that:

- the issue is still open;
- the proposed change matches the issue;
- the change is small enough for one pull request;
- no sensitive information is included in the prompt or repository.

If no suitable issue exists, create one in the next exercise instead of choosing an unrelated change.

## Exercise 2: Create and use a branch

Ask Copilot to prepare a branch, but require confirmation before the write operation:

> For the agreed work in `OWNER/REPOSITORY`, propose a branch name using the format `docs/<short-description>`. Show the target base branch and the proposed branch name. Wait for my confirmation before creating it.

After confirming the names:

> Create the confirmed branch from the repository default branch using the GitHub MCP server. Report the source branch, new branch, and resulting commit or reference.

Verify the branch in GitHub. The branch must start from the expected default branch and use a descriptive, lowercase name.

## Exercise 3: Create or update an issue

If you found an existing issue, use its number. Otherwise ask Copilot to draft a new issue:

> Draft an issue for the agreed documentation improvement. Include a concise title, context, acceptance criteria, and a proposed validation step. Do not create it yet.

Review the draft, then explicitly approve the write operation:

> Create the approved issue in `OWNER/REPOSITORY` with the agreed title and body. Add the label `documentation` only if that label already exists. Report the issue number and URL.

An issue should describe the problem and the expected outcome, not prescribe every implementation detail. Record its number because it will connect the issue to the pull request.

## Exercise 4: Make the change and open a pull request

Make the documentation change locally on the new branch. Review the diff and run any relevant link checker, formatter, or documentation validation available in the repository.

Then ask Copilot to prepare the pull request content:

> Using the changes on branch `BRANCH_NAME`, inspect the diff and draft a pull request with:
> - a concise title;
> - a summary of the problem and solution;
> - validation performed;
> - a reference to issue `#ISSUE_NUMBER`.
> Do not open the pull request yet.

After reviewing the title, body, base branch, head branch, and linked issue:

> Open the approved pull request in `OWNER/REPOSITORY` from `BRANCH_NAME` into `BASE_BRANCH`. Use the approved title and body. Do not merge it. Report the pull request number and URL.

The pull request should clearly connect the three objects in the workflow:

```text
Issue -> Branch -> Pull request
```

## Exercise 5: Review and follow up

Ask Copilot for a read-only review of the pull request:

> Read pull request `#PR_NUMBER` in `OWNER/REPOSITORY`. Check the changed files, description, linked issue, and available status checks. Identify missing validation or risks. Do not modify the pull request.

If the review identifies a documentation gap, ask Copilot to draft a comment first:

> Draft a concise comment for pull request `#PR_NUMBER` explaining the missing validation. Do not post it yet.

After reviewing the text:

> Post the approved comment to pull request `#PR_NUMBER` using the GitHub MCP server. Do not approve, close, or merge the pull request.

Finally, ask Copilot to summarize the final state:

> Read the issue, branch, and pull request created in this exercise. Summarize their current status, URLs, and remaining actions. Do not change anything.

## Safety checklist

Use the following habits whenever Copilot can call GitHub tools:

- start with read-only requests;
- name the exact owner and repository;
- inspect the target branch before creating a branch or pull request;
- ask Copilot to show proposed titles, bodies, labels, and targets before writing;
- confirm each create, update, comment, close, or merge operation explicitly;
- never paste tokens, passwords, or other secrets into Copilot prompts;
- do not ask Copilot to merge or delete unless that action is part of the exercise and has been reviewed;
- verify the result in GitHub after every write operation.

## Completion criteria

You have completed the exercise when you can show:

- one verified GitHub MCP read-only request;
- one branch created from the expected base branch;
- one issue found or created with clear acceptance criteria;
- one pull request opened from the working branch and linked to the issue;
- one review result and, if needed, one approved follow-up comment;
- a final summary that reports the current status without making additional changes.

## Reflection

Discuss these questions:

1. Which requests should always be read-only first, and why?
2. How did explicit confirmation reduce the risk of changing the wrong repository?
3. Which parts of the workflow were delegated to Copilot, and which decisions required human review?
4. What would you change before using this workflow in a production repository?
